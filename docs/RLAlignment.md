# RL alignment protocol (draft v1)

Status: **design draft**. Per-vector capture exists today as `stats.xor_rows`
(`OPGUARD_XOR_ROWS=1`, native segmented kernel). The `xor_vectors` encoding, the
harness records and the `vectors.*` / `rl.*` actions below are specified here
and not yet implemented. The agent workflow that uses them is
[harness/skills/rl-alignment/SKILL.md](../harness/skills/rl-alignment/SKILL.md).

## Division of work

OpGuard and the harness produce **facts**: fingerprints in a fixed format,
records made at known points, and answers to exact-equality questions. The agent
makes **judgments**: which records correspond, whether a gap is fusion or a
fault, which divergence comes first, what caused it. Judgments go back through
the [alignment-map](AlignmentMaps.md) channel with evidence. Every action here
returns `verdict: not_evaluated`. None applies a tolerance or picks a pivot.

## The problem being separated

For a token generated by the rollout engine under policy version `v` and
trained when the trainer is at version `c`:

```
gap        = logp_rollout(v) - logp_trainer(c)
numeric    = logp_rollout(v) - logp_trainer(v)    # same weights, different code: should be 0
staleness  = logp_trainer(v) - logp_trainer(c)    # policy lag: corrected by IS / TIS
gap        = numeric + staleness                   # exactly
```

`numeric` is an infrastructure fact and should be zero when both sides are
built to agree bit for bit. `staleness` is algorithmic. They can only be split by
evaluating the trainer at `v`. When `v == c` (staleness zero), the trainer's own
log-probabilities give `numeric` with no replay.

## Fingerprint format: `lastdim-u32le-v1`

Each captured tensor may carry, beside the default regional fingerprint:

```json
"xor_vectors": {
  "scheme": "lastdim-u32le-v1",
  "vector_bytes": 256,
  "count": 1216,
  "encoding": "base64-u32le",
  "data": "<count little-endian uint32 values, base64>"
}
```

1. Take the tensor's bytes in logical contiguous order (non-contiguous tensors
   are made contiguous; conjugate/negative views are resolved).
2. `vector_bytes = shape[-1] × element_size`; `count = prod(shape[:-1])`.
   Vector `k` is the byte range `[k·vector_bytes, (k+1)·vector_bytes)`.
3. A vector's fingerprint is the XOR of its little-endian 32-bit words. For
   2-byte dtypes, element `2i` is the low half and `2i+1` the high half.
4. Values are unsigned 32-bit. `data` is always this object's base64 string,
   never a scalar or a decimal list.
5. **Merge rule:** XOR of consecutive vector fingerprints equals the
   `flat-u32-le-v1` XOR of their byte range. Vectors merge into token rows,
   regions or the whole tensor, and can be checked against `xor_signature`.
6. Not computed when `vector_bytes % 4 != 0`, for meta/fake tensors and for
   empty tensors; `xor_vectors_skipped` then gives the reason.
7. A zero fingerprint is a valid value but never evidence.

A vector is addressed as `event_ref` + slot (`["inputs", i]` / `["outputs", j]`,
flattened as in alignment maps) + vector index `k`.

Migration from today's `xor_rows`: values are written as signed int32 decimals,
and a single-vector tensor is written as a float scalar. Readers must mask with
`& 0xFFFFFFFF` and accept a scalar until v1 lands.

## Harness records (observed facts)

Recorded by harness hooks at known code points, never inferred by the backend.

| Record | When | Fields |
|---|---|---|
| `forward` | At each model forward entry, on both engines | `counter`, `rank`, `tokens` (T), `token_ranks` (global token indices held by this rank, when sequence-sharded) |
| `rollout_batch` | For each sampled rollout batch | `batch_id`, `sequences`: [`seq_id`, `token_ids`, `positions`, `policy_version` per token, `logprob` per token], `composition` (all sequences co-batched per forward), `engine_flags` (batch-invariant, CUDA graph, attention backend) |
| `trainer_logprob` | When the trainer computes old/current log-probs for a sampled batch | `batch_id`, `policy_version`, `logprob` per token, `engine_flags` |
| `weight_sync` | At every weight push from trainer to rollout engine | `version`, per parameter: name, shape, dtype, `xor_vectors` on the trainer side and on the rollout side (after any repacking) |
| `snapshot` | For sampled versions only | `version`, location of the saved weights or the checkpoint step that equals them |

`policy_version` is per token. A sequence whose tokens carry more than one
version (weights updated mid-generation with the KV cache kept) is mixed and is
never split as if it had one version.

## Backend actions (facts only)

All follow the protocol v1 envelope in [AgentTools.md](AgentTools.md).

| Action | Input | Returns |
|---|---|---|
| `vectors.describe` | an event | per slot: shape, dtype, `vector_bytes`, `count`, optionally the first N fingerprints |
| `vectors.lookup` | a fingerprint, or a slot + vector index; a scope (side, ranks, counter range) | every exact occurrence: run, rank, event, slot, vector index |
| `vectors.coverage` | a slot | for each vector, whether and where it occurs on the other side |
| `vectors.compare` | two slots plus token dims declared by the agent for each | per token row: equal, or the indices of the differing vectors |
| `rl.decompose` | `rollout_batch`, the `trainer_logprob` records available | per token: `numeric` and `staleness` where computable, exact-zero flags, `mixed_version` flags, and which records each value came from |
| `rl.weight_sync_check` | a `weight_sync` record | per parameter: rows equal, or the differing row indices; rows matched by fingerprint so repacking is not a difference |
| `rl.replay_request` | a `rollout_batch`, a version, a side (trainer / rollout), `composition: original \| batch_invariant`, capture options | a workload request for the existing experiment stages that recomputes the batch at that version. It does not run it. |

`rl.replay_request` with `composition: batch_invariant` must say so in its
result: such a replay localizes implementation differences, not the specific
error of the original run.

## Online and offline

- **Online:** recording only, plus `numeric` at staleness-zero points (no replay
  needed). Nothing changes the training job's weights or schedule.
- **Offline:** replays at a recorded version, per-vector recapture
  (`OPGUARD_XOR_ROWS=1`) of selected batches on both sides, and every agent query.

## What this does not decide

Which operator corresponds to which, whether an unmatched row is fused away or
wrong, how tokens moved across ranks when no record says so, and which
divergence is first: these are the agent's, with evidence, as described in the
skill. The token-chain matcher (`perfetto/token_match.py`) is a reference
policy an agent may run and check, not a backend verdict.
